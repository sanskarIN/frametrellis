# FrameTrellis v1.2.1 — staged maintenance plan

Status: **final validation and publication in progress**. See the
[v1.2.1 release notes](../releases/v1.2.1.md); this plan records the
investigation's known limitations rather than claiming a confirmed crash fix.

This maintenance version follows v1.2.0, not v0.2.1. Treat every phase as an independently reviewable set of commits. Do not advance the release milestone without validation.

## Phase 1 — investigate intermittent ARM64 portable GUI startup (in progress)

A v1.2.0 post-release Windows package check on Windows 11 ARM64 failed once while the portable x64 editor displayed its test project: access violation 0xc0000005 in Qt6Core.dll. The installed editor and render helper passed in the same run, and rerunning the failed job passed. **The underlying defect is not confirmed or fixed.**

- [ ] Capture actionable Qt and editor startup/shutdown diagnostics on failure, without suppressing failures.
- [ ] Exercise independent portable launches on the Windows ARM64 validation runner. Each launch must pass; no retry-as-success rule.
- [ ] Preserve the original strict package-boundary and checksum checks.
- [ ] Add coverage for failure paths and confirm successful Linux/Windows CI.

Implementation checkpoint (CI verification still pending): the Windows package
verifier now rejects sibling-directory path prefix matches, refuses to treat a
failed module scan as success, clears stale screenshots before each GUI launch
and has a dedicated PowerShell path-boundary regression suite in package CI.
These are test-harness hardening changes, not evidence that the ARM64 crash
root cause is fixed.

## Phase 2 — identify and fix any reproducible root cause (not started)

- [ ] Reproduce and isolate failure to Qt initialization, rendering, plugins, media/audio, or shutdown.
- [ ] Make narrowly scoped C++ lifecycle changes only when backed by tests.
- [ ] Confirm no regression to GUI open/save/export or existing editing features.
- [ ] Document remaining hardware/emulation limitations honestly.

## Phase 3 — release readiness (not started)

- [ ] Decide and implement remaining maintenance fixes based on Phase 1/2 evidence.
- [ ] Finalize version bump, changelog, packaging, clean-machine tests and release assets.
- [ ] Obtain green required CI and explicit release decision before tagging/publishing.

## Future v1.2.2 — distribution planning only

A possible WinGet listing/update workflow is **deferred to v1.2.2**. This branch does not add WinGet manifests, package IDs, submission workflows or package-manager automation. That milestone will require verified public installer URLs, stable package identity, correct installer metadata and a separate submission/review.
