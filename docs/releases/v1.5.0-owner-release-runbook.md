# FrameTrellis v1.5.0 — owner's manual GitHub release runbook (NOT APPROVED)

> **Release hold:** This is a procedure for a **future** owner-approved stable
> release, not authorization to publish. The published stable version is v1.4.0.
> Do **not** create tag `v1.5.0`, click **Publish release**, or paste the
> `FrameTrellis-1.5.0-OWNER-APPROVED` confirmation line before independent
> release acceptance and explicit approval from the owner.

This is the **14-file, three-OS** process. Never use the legacy
[Windows-only five-file instructions](manual-publication.md) or rename
experimental packages to make them look like production files.

      disposition. A closed issue and passing synthetic CI are not proof.
- [ ] Resolve or record an evidence-backed release disposition for the intermittent
      Windows 11 ARM startup crash [#185](https://github.com/sanskarIN/frametrellis/issues/185).
- [ ] Complete native Windows x64 tests with real audio, saved project recovery,
      consecutive long exports, cancellation, varied media and free disk space.
- [ ] Build **production** Linux x86_64 AppImage with clean-host GUI, audio
      and real MP4 verification; complete bundled runtime, SPDX 2.3 and source TAR.
- [ ] Build **production** macOS arm64 and Intel x86_64 DMGs with trusted
      Developer ID identity, hardened-runtime signing, Apple notarization/stapling,
      verified Gatekeeper acceptance on clean native Macs, physical playback,
      real exports, SPDX 2.3 and corresponding source TARs. Ad-hoc-signed,
      unnotarized development DMGs are **not** production packages.
- [ ] Record every third-party component and correct Corresponding Source,
      license text, source download and SBOM relationship on all platforms.
- [ ] Review the complete v1.5 scope; set `CMakeLists.txt` to `VERSION 1.5.0`;
      finalize `docs/releases/v1.5.0.md` without DRAFT/NOT RELEASED markers.
- [ ] Merge only validated PRs, freeze one exact protected `main` 40-character
      SHA and ensure the full CI, Windows packages, Linux/macOS desktops and
      packaging tests pass **again at that SHA**. Any further merge invalidates
      the freeze and requires fresh builds/tests.

`package-macos-experimental.yml` workflows do not emit production artifacts,
and the CMake project is still 1.4.0. The candidate collector cannot pass yet.

## Gate 3 — prepare the nonpublishing verified 14-file candidate

1. Go to [repository Actions](https://github.com/sanskarIN/frametrellis/actions)
   and choose **Prepare v1.5 three-platform candidate (NOT A RELEASE)**.
2. Select **Run workflow**, use the `main` branch, and fill
   `source_sha`, `windows_run`, `linux_run`, `macos_arm64_run`, and
   `macos_x86_64_run` from Gate 2. Then start that workflow.
3. It validates current `main`, release version/notes, authenticated CI runs,
   the provider-reported artifact ZIP SHA-256 digests, safe extraction, all
   platform payloads, SPDX structure, source TAR structure and `SHA256SUMS.txt`.
   It **does not** tag, publish, sign, notarize or approve a release.
4. Require a successful job and download its **single unexpired** artifact:
   `v1.5.0-three-platform-candidate-NOT-APPROVED-NOT-RELEASED`.
   It has short retention; do not let it expire before publishing.
5. From the repository checkout at the *same* frozen SHA, independently check
   the extracted candidate **without placing extra files inside its folder**:

   ```bash
   python3 packaging/verify_candidate_matrix.py --version 1.5.0 --directory /path/to/candidate
   cd /path/to/candidate && sha256sum --check SHA256SUMS.txt
   ```

   On Windows, the Python verifier remains available; use an environment
   containing `sha256sum` for the manifest check, or verify the same SHA-256
   values independently. Archive integrity cannot substitute for physical
   tests, Apple notarization or source licensing.

## Gate 4 — manual owner creation in GitHub (ONLY AFTER APPROVAL)

The owner must confirm that every gate above passes, that the frozen main SHA
has not changed, and give **separate, explicit approval** to publish stable
v1.5.0. Then:

1. Visit [FrameTrellis Releases](https://github.com/sanskarIN/frametrellis/releases)
   while signed into the repository owner's GitHub account.
2. Select **Draft a new release**.
3. **Choose a tag:** enter `v1.5.0`. Create it from `main` **only if**
   the selected `main` still equals the tested frozen SHA. If not, STOP.
   An existing `v1.5.0` tag is acceptable only when it points to the
   identical verified commit. Do not move or reuse another release's tag.
4. **Release title:** `FrameTrellis 1.5.0 — Featured Release`.
5. **Description:** use the approved, final content from
   `docs/releases/v1.5.0.md` (not its DRAFT version), with the separate
   confirmation line shown below **only after explicit owner approval**:

   ```text
   FrameTrellis-1.5.0-OWNER-APPROVED
   ```

   This marker must be an **exact standalone line**; it is a final release
   authorization signal to the automated attachment workflow.
6. Leave **Set as a pre-release** *unchecked*. Select **Set as the latest
   release** when that UI option is present.
7. **Do not manually attach partial or old files**: the v1.5.0 uploader requires
   an empty release and automatically uploads the full verified 14-file set.
8. Only after the above conditions have been independently checked, select
   **Publish release**. The tag and stable release become **public immediately**;
   the files are attached afterward, not before.

**Publication hazard:** even with all gates passed, this workflow briefly
publishes a release without binaries, until the attachment run finishes.
If attachment fails, the public release remains incomplete. Stop promotion,
check the failed workflow and reconcile the exact candidate; never silently
mix assets from different source commits or rerun over a partial release.

## Gate 5 — verify public release and website before announcing

1. In [Actions](https://github.com/sanskarIN/frametrellis/actions), confirm
   **Attach approved v1.5.0 three-platform assets** succeeded, *not* the
   legacy five-file uploader.
2. On [the v1.5.0 release](https://github.com/sanskarIN/frametrellis/releases/tag/v1.5.0)
   count **exactly 14** downloadable assets. Check expected names, sizes,
   `uploaded` states and GitHub SHA-256 digests against the downloaded
   candidate. The workflow calls `packaging/verify_published_candidate.py`.
3. Confirm `v1.5.0` and `main` both point to the frozen approved SHA,
   not a newer commit or a PR head.
4. Independently download each native package, verify its checksum, install
   on supported clean hardware, launch both the editor and renderer, and
   test a short and representative longer export with real sound.
5. Check that the official site points to the verified public release and
   assets; do not announce from a stale or missing download link.
6. Only after those checks pass, announce stable v1.5.0 publicly.
